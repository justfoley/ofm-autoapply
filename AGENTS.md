# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- Build/test: `npm test` (Node's built-in test runner, no deps to install). See `README.md`'s "Development" section for the exact invocation and coverage. Load-unpacked steps also live in `README.md`.
- Architecture: `lib/*.js` holds pure, unit-tested logic (dedupe, category-filter, log, storage, posting-parser, apply-eligibility, activity); `background/service-worker.js` orchestrates them via `chrome.alarms`; `popup/` is the UI. `lib/feed.js`/`lib/apply.js` are the one exception — they contain small, deliberately-untested DOM-walking functions (`extractRawCardsFromPage`, `getCardApplyState`, `clickApplyButtonForPosting`) that run inside a real tab via `chrome.scripting.executeScript` and must stay self-contained (no closures/imports survive that serialization boundary). `content/overlay.js` (see below) is a second, deliberate instance of that same exception. Keep new logic in `lib/` and unit-testable where possible.
- **Live "current activity" status** (idle/polling/applying-to-X + next-alarm timestamp) lives in `lib/activity.js`, stored under its own `chrome.storage.local` key (`ACTIVITY_STORAGE_KEY`) separate from `lib/storage.js`'s `STORAGE_KEY`, so fast-changing poll-cycle phase transitions never touch the settings/log blob or its `storage.onChanged` listener. `background/service-worker.js` writes a transition on every phase change (polling at cycle start, applying per posting, idle in a `finally` so it always resets even on error); `popup/popup.js` and `content/overlay.js` both read/subscribe to it via `chrome.storage.onChanged`. The per-second countdown is never written to storage — `nextAlarmAt` is a fixed target timestamp, and each reader recomputes `secondsUntil()` locally on its own 1s timer (see `lib/activity.js`'s top comment before changing this).
- **Tab overlay** (`content/overlay.js`, registered in `manifest.json`'s `content_scripts` for `https://ofmjobs.com/*`): full-tab blurred lock while a poll cycle is active, small corner countdown while idle, nothing when the master switch is off. It duplicates a few of `lib/activity.js`'s pure functions inline — no imports survive either the manifest content-script or the `chrome.scripting.executeScript` injection path — so keep the two in sync if the activity-record shape or wording changes. Declarative `content_scripts` only auto-inject into tabs that load/reload after the extension does, so `background/service-worker.js`'s `injectOverlayIntoOpenTabs()` also best-effort injects it into already-open matching tabs on `onInstalled`/`onStartup`.
- The real ofmjobs.com feed/apply flow was never inspected with a working browser (`chrome-devtools-axi` had no Chrome install) — implementation is based on a captain-supplied authenticated DOM dump of the dashboard jobs page, plus the captain's confirmation (relayed via firstmate) of what a real Apply click does. See README "What was confirmed" / "Still open" before touching `lib/feed.js` or `lib/apply.js`: the feed page's own URL is inferred, not observed, and marked `TODO(unconfirmed)` in code.
- A posting can carry **multiple** categories at once — `posting.categories` is always an array; `lib/category-filter.js` matches on intersection, not equality.
- `lib/categories.js`'s `DEFAULT_CATEGORIES` is a seed only (9 values actually observed in the DOM dump, not proven exhaustive). The popup's real checkbox list is `state.knownCategories`, which `background/service-worker.js` grows from every posting it sees — don't reintroduce a fixed/static category list in the UI.
- Apply confirmed to submit immediately in place (no modal/form) **only for a posting with no application questions/tests**; whether the captain qualifies on other grounds is a server-side judgment invisible to the client, so `lib/apply-eligibility.js` does not gate on posting content beyond that. A posting whose feed card carries a "N questions"/"N tests" badge (`Posting.questionCount`/`testCount`, `lib/posting-parser.js`, scraped in `lib/feed.js`) is never auto-clicked at all — `canAutoApplyPosting()` catches it before `lib/apply.js` opens a tab. `canClickApply()` then covers whether the DOM lets the extension act at all on what's left. Outcome is one of four states — `applied` / `applied-unconfirmed` / `needs-manual` / `needs-questions` (`interpretPostClickState`, `describeUnexpectedApplyState`, `lib/log.js`) — never assert `applied` without an observed DOM signal, and never let a click that surfaced a dialog or navigated away read as one either (`interpretPostClickState`'s post-click backstop, checked before its other branches). See README.md's "Application questions and tests" for the live evidence this is based on and what's still unconfirmed (the real authenticated answer-entry form's shape).
- **Popup visual design** (`popup/popup.css`) uses real tokens pulled from ofmjobs.com's live site (public marketing pages, cross-checked against the captain-supplied dashboard DOM dump — see above) rather than a generic extension look: brand green `#2e8053` (`--om-primary`), the Hanken Grotesk typeface (bundled locally as woff2 in `popup/fonts/`, OFL-licensed, so the popup never depends on a network font fetch), shadcn-style neutrals (`--om-bg #fafafa`, `--om-border #e5e8e6`, `--om-text-muted`), a 3-step radius scale (`--om-radius-sm/md/lg` = 8/12/16px, plus full-pill for the toggle), and the dashboard's soft-badge pattern (pastel background + matching saturated text) for both category state and the activity log's outcome pills. Reuse these custom properties for any other popup-adjacent UI rather than inventing new colors/radii. The technical DOM-dump caveat that used to sit in a banner on the main view now lives in the collapsed `<details class="about">` block at the bottom of `popup.html`; the activity log's raw outcome strings (`applied`/`applied-unconfirmed`/`needs-manual`/`needs-questions`) are still what `lib/log.js` produces — `popup/popup.js`'s `BADGE_LABELS` is where they get reworded into captain-facing copy, so update that map (not `lib/log.js`) if the wording needs to change again.
